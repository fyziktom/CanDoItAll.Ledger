# Assumptions And Risks

## Assumptions

- The already-running node exposes public read APIs and write/broadcast APIs consistent with the AccountApp configuration.
- Alice and Bob import files and funded balances from previous bundles remain available or can be regenerated by existing scripts/docker compose.
- A BO sale can be modeled as ledger-visible BO state and signed BO transactions without changing consensus rules.
- The first implementation must support main-currency sale price. Token-priced UI can remain disabled unless the adapter implementation can build the required token payment transaction safely in this bundle.
- 2L semi-smart contracts are optional architecture support. They should not be introduced unless they reduce complexity or improve idempotency within this bundle.

## Critical Path Risks

- `CPR-01`: Long-text proof is a prerequisite for commerce because sale, payment, purchase, and receipt payloads need reliable structured state display and raw-state visibility.
- `CPR-02`: Commerce state contracts are a critical foundation. If sale terms or payment status are ad hoc JSON wrappers, Buy page and dispatch automation can pass shallow UI checks while failing real lifecycle behavior.
- `CPR-03`: Dispatch is idempotency-sensitive. Duplicate refresh loops, browser reloads, or failed mid-chain transactions must not create duplicate original transfers or excess clones.
- `CPR-04`: Ledger projection supports one transaction payload envelope. Any design that tries to create multiple unrelated BO states in one transaction can corrupt projection semantics.
- `CPR-05`: Shared SSR/WASM components must not drift. If AccountApp-only UI bypasses shared components, Node/SSR demos and future reuse become unreliable.

## Validation Risks

- Browser UI may appear correct while raw BO state omits long text or sale terms. Tests must assert serialized payloads and node query results.
- Playwright may pass by creating fixture objects directly instead of using production UI. Browser proof must use the AccountApp UI for create/list/sell/share/buy/dispatch checks.
- A positive buy test without duplicate-refresh negative proof would not prove idempotency.
- A receipt list count alone does not prove records link to the purchased BO or open the correct detail dialog.

## Reopen Triggers

- Reopen `SB01` if any commerce record field is not visible in details or raw state.
- Reopen `SB02` if browser implementation needs unplanned commerce state, status, or record kinds.
- Reopen `SB03` if Playwright finds dialogs clipped, buy link cannot load by API, or local vault unlock cannot resume purchase.
- Reopen `SB04` if seller refresh duplicates dispatch, ignores max clone limits, or processes payments without matching sale terms.
- Reopen `SB05` if Alice/Bob end-to-end proof must be manually seeded outside production flows.
